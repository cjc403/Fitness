# 网页 Agent 消息任务修复（2026-10-16，本地）

## 原因

本轮针对“打开站内消息，给指定用户发送消息”的任务复现并修复了三处缺口：

1. **看得见联系人，却没有可点击的控件引用。** 原联系人和已有会话使用普通 `li @click`，DOM 执行器识别按钮等标准控件，未将它们纳入可执行列表。隔离真实页面中，联系人已经显示，但观察结果缺少该对象，回归测试先失败后通过。
2. **发送成功的实际回执没有进入下一轮规划。** 原 `onReceipt` 只更新面板步骤，而模型收到的是 `history` 中的“点击发送”。真实店长验收中，消息已成功写入一次，模型仍要求再次确认是否成功。现将已经人工确认的真实业务成功/失败反馈写入规划历史，不依靠页面文字推测结果，也不通过口头答复认定成功。
3. **暂停没有说明原因。** 原界面只显示“已暂停”。现区分手动暂停、网页隐藏、助手关闭或重新加载、断网；保留首次原因，继续时恢复原状态。待确认请求不会因为“继续”自动放行。旧版没有记录原因，因此不能追溯截图中那一次暂停的具体触发动作。

## 改动

- 共享 ChatPanel 的员工、会员联系人及已有会话改为原生按钮，保留业务加载、草稿和发送逻辑；支持键盘访问、焦点提示，并为执行器提供姓名、角色及账号编号。
- 会话标题显示账号编号，实际请求预览将 `recipientUserId` 显示为“收件人账号编号”，便于核对对象。
- 只有请求确认门槛放行、HTTP 与业务结果成功时才报告成功回执；确认、权限、停止、旧回调阻断和禁止重放的机制仍生效。
- 复用现有 `observe` 反馈协议向模型传递实际回执，没有新增任意脚本、直接业务 API 执行或后台权限。

证据目录：`docs/qa/page-agent-chat-20261016/`。

| 验证 | 结果 |
|---|---|
| 前端全量单元测试 | 254/254，无跳过、失败或取消 |
| vue-tsc 与 Vite 构建 | 通过；既有主包超过500kB提示保留 |
| 总部、店长、前台、教练、顾问、会员真实模型 | 六角色全部完成同页消息任务 |
| 真正发送 | 每例确认前0条、确认后1条，实际请求正文及收件人完全匹配 |

| 后续模型反馈 | 每例实际收到“人工确认已完成；业务提交成功”回执，再结束任务 |
| 浏览器错误与越界来源 | 均0 |
| 独立只读审查 | 两轮无重要发现；任务引擎相关17项独立通过 |
| 正常本地开发入口 | 5173端口的新消息组件、任务组件均200，只读核对 |

完整角色数据在 `model.json`，修复前证据为 `probe-before-fix.json` 和 `model-missing-receipt.json`。`model-first-attempt.json` 记录初次测试过早读取异步确认状态的断言问题，测试已改为等待原确认真正放行，不能把该文件当作最终验收结果。后续单独核对可见“已完成”状态，记录在 `visible.json`。

所有测试消息仅写入4177→18080代理及带 `qaDatabase=agent_browser` 标记的独占隔离库。没有给真实 `cjc2` 用户补发或重发消息。后端 Java/JAR 与23个既有迁移没有修改，本轮不重跑后端包；未更新服务器或推送。

## 使用

刷新当前网页后重新发起任务，例如“打开站内消息，给 cjc2 发送‘你好啊’”。刷新会清除未提交的表单和内存任务。执行期间保持助手及当前标签页打开；如暂停，界面会说明原因，点“继续”恢复。出现请求预览时，核对收件人编号、消息原文后点“确认并提交这一次”，等待“已完成”。

本轮验收覆盖上述消息流程；其他复杂业务仍需页面提供可识别控件，并分别验证完整操作链。
