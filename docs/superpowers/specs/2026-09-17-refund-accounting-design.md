# 下一阶段第一批：剩余权益退款、审批与对账设计（待用户确认）

## 1. 范围与现状

上一阶段已实现私教课包预占、本人签课、正式消课和月结。本阶段总体包括剩余权益退款、结算调整、精确金额与财务报表；为隔离资金状态，分两批设计、实现和发布。

第一批交付：剩余价值核算、退款申请/审核/支付登记、流水对账与导出。第二批交付：已审核教练月结的调整单，不直接重写原月结。本文件只规定第一批，不把第二批未实施功能描述为已交付。

现有实现存在以下限制：

- `CommercialService.refund` 只核对来源订单的实收减退款，不处理续费对应的权益资金归属；部分退款时原剩余次数不变。
- 私教 `lessonUnitPrice` 按两位小数反复平均，最后一节没有精确余额结清机制。
- `overview` 按订单的收款月份计算实收减累计退款，无法正确反映跨月实际退款。
- 历史续费操作没有明确关联新续费订单与原权益；商品字段也未在权益中保存不可变类型快照，不能无依据自动推定历史退款金额。

## 2. 方案比较与选择

方案 A：仅把现有退款按钮改成审批。改动少，但余额、续费和金额尾差问题仍在，不能作为本批方案。

方案 B（推荐）：在现有 commercial 模块旁增加 finance 子模块，新增权益价值账、资金来源关联、退款申请和流水分摊；商业销售/消费入口调用同一价值服务，历史记录保留。成本适中，能够验证权益、金额及退款的对应关系。

方案 C：立即重建完整复式会计、支付网关、工资系统。依赖业务会计政策及支付主体资料，不适合当前个人学习阶段，也不在本批实施范围。

采用 B。新模块拆为价值计算、退款生命周期、报表三个职责清晰的服务，不继续把所有逻辑塞进现有 CommercialService。

## 3. 用户可见的退款规则（建议默认值）

### 3.1 退剩余服务并终止权益

本批的“部分退款”指总价中未使用部分的退款，例如十节课已上两节，只退剩下八节的服务价值并终止课包，不是任意退一笔钱却继续保留八节。暂不实现“只退三节、保留另外五节”的按数量拆包。

- 次卡和私教包：按经过核对的未消费资金余额核算，不按商品当前标价或原价重算已消费部分。
- 月卡/季卡/年卡：按未使用有效服务日计算；本批采用服务日均匀分摊，不根据扫码次数推定时间卡已经消费多少金额。
- 时间卡以 Asia/Shanghai 日历日期为准，完整过去的有效日计为已使用，当天计入剩余可退服务日。当天开卡、当天申请可退未使用金额。冻结日不计已使用服务日，未来尚未开始的续费服务期也可退。
- 商品更新、续费及转卡不能改变已经确认的历史消费金额。未来续费保存独立金额、权益类型及服务量快照。
- 默认退款手续费与违约扣款均为 0，不擅自设定惩罚费用。本批不提供任意修改退款规则的入口；以后有明确合同政策时再做版本化配置。
- 过期课包如仍有可核对的剩余资金，可以申请并由管理员按事实审核，不自动把余额当作收入或没收；剩余有效服务日已经为零的时间卡不生成正数退款建议。
- 退款不能超过权益未使用价值，也不能超过关联来源订单尚未退款的实际收款。余额为零时禁止提交零元资金退款。

以上是系统建议的学习用业务规则，不代表已通过合同、税务或法律合规审查。

### 3.2 历史权益的处理

已有账号、订单、会员、消费快照和权益次数不修改。新增迁移不使用来源订单价格乘剩余次数来自动冒充精确历史余额。

- 新销售/续费生成有明确来源的价值记录。
- 历史权益先标记“待核对”，显示原有业务信息及核对提示；不得把估算值计入已核实余额合计。
- 总部/店长可进行一次性余额核对：关联可证实的来源订单、填写未使用金额和核对原因，保存操作人、时间和原始库存快照。未使用金额不得超过关联订单净实收。
- 无法确认历史续费归属、已有退款与原权益的关系时，阻止资金退款并说明原因，不猜测、不删历史。
- 同一来源订单只能归属一个权益资金账户；核对时检查原交易和已有分摊，不能让两张卡同时使用同一笔可退资金。转让过的权益须由总部核对持有人、原收款凭证及退款受领依据，本批不根据当前持有人自动推定原付款人或收款账户，资料无法核实时不办理资金退款。
- 未核对不影响原有浏览、预约和正常服务；后续消费/续费事件仍记录，退款则必须先核对。旧私教已签课金额快照不重算。
- 基准核对及申请审核时必须重新锁定权益，库存或退款状态已经变化时旧预览不可执行。

## 4. 精确金额与流水

- 金额以整数“分”作为内部余额和分摊单位；API 展示人民币两位小数。非法小数位、负金额和溢出在写订单前拒绝，不依赖数据库截断。
- 新次卡/私教包实际消费：当前未使用资金余额除以当前剩余次数，按分四舍五入；最后一次消费扣除全部剩余余额。预占不是实际消费，不减资金余额。
- 续费把新增实收加入未使用价值，不重算已消费快照。冲正恢复原次课实际扣除的金额，不能恢复现在的平均单价。
- 私教提成继续使用该次实际消费金额和签课时提成比例，金额变更不追溯改已经确认的旧课。
- 新时间卡保存每次开卡/续费的资金来源及服务日区间，按日精确分摊，尾差归最后服务日。冻结暂停服务日消耗，解冻顺延尚未使用的服务区间，不修改已经消费的金额；同日冻结/解冻不凭空赠送收费服务日。
- 来源资金的消费和退款分摊按各来源未使用余额比例计算，先取整数分，再按小数余数从大到小补余分，同余按来源订单 ID 排序；分摊和严格等于本次金额，且单来源不得超过其未使用金额。
- 一个退款执行可能对应多个来源订单，分别增加订单 refundedAmount 并生成退款流水；退款单、订单及流水均有明确关联，不把所有退款塞到最初订单。
- 价值账采用追加事件：开卡、续费、消费、冲正、时间服务消耗、余额核对、退款。旧事件不删改，重试使用业务事件唯一键避免重复资金变化。
- 已退款权益不能通过旧冲正入口恢复为可使用状态；退款与冲正发生竞态时只有满足最新状态的一方成功。退款终止卡并清零剩余次数，保留原历史库存快照。

## 5. 退款状态和权限

状态：PENDING（待审）→ APPROVED（待登记支付）→ PAID（已登记退款）；PENDING 也可 REJECTED 或 CANCELLED。拒绝/撤回后再次提交产生新申请，保留旧申请。

1. 前台、店长、总部可为有权限访问的会员提交；本批会员本人只查看自己退款进度，暂不公开自助发起，以避免额外涉及收款账户信息。
2. 提交时核对无预占课次、无未完成服务预约、无待签课；时间卡也检查未完成团课/普通预约，不能只看 private_lesson。有关预约需先由合适角色正常取消/处理，不自动删除。
3. 每个权益最多一个 PENDING/APPROVED 申请。提交后单独标记“退款办理中”，不改原权益业务状态；阻止使用、预约、续费、冻结/解冻、转卡、签课和冲正，防止金额审批期间继续变化。查询仍可用；拒绝或撤回释放该办理标记。
4. 申请提交日固定服务停止及价值截止日，审批等待不会继续消耗时间卡价值。拒绝/撤回时恢复服务并顺延实际暂停的服务日，不把暂停期当作正常消费。
5. 店长审核本门店前台提交的申请；总部可跨门店审核；申请人与审核人必须不同。店长或总部本人提交的申请由另一位有范围权限的管理员审核，不允许自审。无其他可用审核人时提示原因，不绕过限制。
6. 审核同意、拒绝均须原因；退款金额从服务端价值快照计算，管理员不能任意放大。提交/批准/支付登记均校验权益归属、来源订单可退余额及申请状态。
7. APPROVED 只表示业务同意，不表示钱已经退。店长/总部凭线下真实退款凭证登记 PAID；需退款渠道、外部凭证编号、时间和备注。渠道只作为记录，绝不自动调用微信/支付宝/银行。
8. 凭证编号按渠道唯一，登记金额必须与批准金额一致。重复请求返回原结果，不二次写流水；来源订单及权益变化在一个事务内提交。
9. APPROVED 不允许前台直接撤回；如尚未付款需取消，由总部填写原因，留审核日志并解除办理标记；已经 PAID 不删除、不直接改回未支付。本批不处理已付款退款撤销或真实支付冲正。
10. 教练不访问会员退款资金、凭证或财务报表。会员仅访问自己申请的金额及进度，不返回员工提成、操作人员个人资料或外部资金凭证。

## 6. 数据和接口边界

新增 Flyway V9，仅加字段和新表；V1–V8 校验和不变。建议新表职责：

- `entitlement_value_account`：已核对/待核对、未使用资金余额、服务量、办理中申请、金额版本与基准快照。
- `entitlement_funding`：来源订单、权益关联、实收和服务类型/数量/日期快照、剩余资金。
- `entitlement_value_event`：追加式金额变动、库存变动、来源业务键、操作人和发生时间。
- `entitlement_term_period`：时间卡资金服务日、冻结/办理暂停区间，用于保留不同续费段和历史服务日。
- `refund_application`：范围归属、申请/批准/登记快照、原因及人员、时间、客户端幂等键、状态。
- `refund_allocation`：申请到资金来源、订单及退款流水的分摊。
- `refund_audit`：完整动作历史，不把新退款审计混入不可区分的旧操作备注。

入口 `/api/v1/finance`：GET 权益退款预览、POST 历史余额核对、POST 申请、GET 范围内申请列表、POST 审核/拒绝/撤回/登记支付、GET 收退款与未使用价值报表、GET UTF-8 CSV 导出。会员本人读取路径独立，所有范围由服务端会话确定，不能信任前端传入会员 ID。

新增 REFUND_REQUEST、REFUND_APPROVE、REFUND_PAY、VALUE_RECONCILE、FINANCE_REPORT_READ 等独立权限；角色矩阵与前端菜单来自同一目录。前台不因已有 FINANCE_READ 获得审核/登记支付权。

旧 `/commercial/entitlements/{id}/refund` 禁止继续直接执行资金退款，返回明确提示转新申请流程，不存在绕过审批的后门。前端原退款按钮切换到预览/申请，保留查阅旧退款流水。

## 7. 并发、金额安全与错误处理

沿用门店写锁防止预约与退款交叉；需要已有预约记录时保持门店 → 排课 → 教练（必要时）→ 权益的顺序。价值账户、退款申请、来源资金及订单放在权益之后，多个来源按 ID 排序，不从财务账户反向获取教练锁。月结服务不反向等待退款锁。

在同一事务中重新读取锁后的状态，幂等键唯一约束兜底；不能先读旧余额、审批完成后再用旧结果退款。避免跨服务捕获事务异常后继续提交半套流水。

鉴权沿用现有401/403与令牌刷新，不把资金状态错误包装为“权限不足”。业务失败按统一 code 返回解释；列表请求失败有错误状态和重试入口，不能展示假的零数据。所有操作人取会话，金额以服务端为准，日志不写密码、令牌、银行账户或整份私密凭证。

## 8. 财务报表

- 实际收退款按 payment_transaction.occurredAt 所属月份、渠道和门店汇总，不按原订单月份减累计退款。
- “净收款”=期间成功收款−期间成功退款；“未使用服务价值”单列，不称为利润或直接当作已实现收入。
- 新已核对资金的服务消费值单列，历史未核对数与金额缺口明确提示；不得把未知金额填成零来通过对账。
- 订单累计实收/退款、流水合计、权益价值事件、退款分摊的差异列表可追到原记录。差异只报告，不自动改真实数据。
- CSV 导出由同一查询范围和时间口径生成，转义引号/换行，并防止以 =、+、-、@ 或控制字符开头的文本产生电子表格公式注入。限制最大导出量，超限提示缩短日期范围。
- 暂不提供税务报表、总账/试算平衡表、真实发票红冲、合同自动变更或支付网关对账。

## 9. 验收与发布

必须覆盖：10元/3次尾差结清；消费后续费与冲正；被冻结时间卡与未来续费段；申请期间禁止使用；拒绝/撤回恢复；无自审；跨门店/跨会员访问拒绝；同权益并发申请；并发重复支付登记；跨月收退款统计；多来源退款分摊；旧入口不能绕过审批；历史待核对不会被自动当作精确金额；CSV 注入；原私教27项测试保持通过。

本地先运行后端全套测试/打包、前端类型检查/构建及浏览器角色流程，再在独立 PostgreSQL 库验证新迁移、约束及并发。测试禁用付费 AI。

生产发布前备份数据库、旧后端与旧前端，验收制品摘要绑定上传包。生产只验登录、角色权限、只读数据与资源，不对真实会员做消费/退款验收。失败恢复旧应用，不自动覆盖正在使用的数据库；兼容性新增结构保留。通过后保存证据及回滚路径，并停止临时测试服务。
