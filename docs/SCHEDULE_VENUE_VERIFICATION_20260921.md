# 排课门店归属修复验证记录

状态：**前端修复完成并构建通过，尚未发布。** 未改后端、未改数据库、未写任何业务数据、未触碰服务器。

## 一、现象

管理员（总部视角）在「课程与排课 → 新增排课」里创建了两条排课（9 月 26 日「私教体验课」、9 月 28 日「核心训练营」），
管理员列表里显示「可预约」，但会员端「未来 30 天可预约课程」显示 **0 场可选**。

## 二、根因

系统里有两条互不相干但叠加生效的规则：

1. **排课的门店 = 课程的门店**。`CourseService.createSchedule` 用
   `venueId = request.getVenueId() == null ? course.getVenueId() : request.getVenueId()`，
   随后强制校验 `course.getVenueId().equals(venueId)`，因此排课的门店完全由所选课程决定。
2. **会员只能看到本门店的排课**。`MemberPortalService.schedules()` 查询条件是
   `venueId = 会员所属门店` 且 `status = 'SCHEDULED'` 且 `scheduledStartTime ∈ [now, now+30d]`。

本地库实测：

| 对象 | 值 |
| --- | --- |
| `venue` | id=1 **总部**（HEADQUARTERS）、id=2 **FitChain 滨江店**（BINJIANG） |
| 会员 cjc2（FC2026000019） | `venue_id = 1`（总部） |
| 新建排课 id=23 / id=24 | `venue_id = 2`（滨江店） |
| 所选课程 id=9 / id=10 | `venue_id = 2`（滨江店） |
| 总部（venue=1）未来 30 天的可约排课数 | **0**（旧排课 13–17 落在 9/15–9/19，均已过期） |

所以会员端「0 场可选」是正确的门店隔离结果；**真正的缺陷在前端**：新增排课弹窗既没有「所属场馆」字段，
课程下拉又用全量 `courses` 渲染（超级管理员能拿到所有门店的课程），近期排课表格也没有门店列——
操作者完全无从知道排课会落到哪个门店。

## 三、修复内容（仅 `fitness-frontend/src/views/admin/CourseManagement.vue`）

- 新增排课弹窗增加「所属场馆」：超级管理员可选（默认取第一个有课程模板的门店），**课程下拉按所选门店过滤**；
  非超级管理员不显示该字段（后端本就按其门店限权）。
- 选择课程或开始时间后，**结束时间自动 = 开始时间 + 课程时长**（可手动调整），顺带消除手填成次日 00:00 的问题。
- 近期排课表格为超级管理员增加「门店」列；课程库卡片为超级管理员显示所属门店标签。
- 时间列对跨天排课显示结束日期（如 `9月29日 00:00`），不再只显示 `HH:mm`。
- `listVenues()` 用 `.catch(() => null)` 兜底：前台/教练等没有 `VENUE_READ` 的角色进入本页不会因为 403 整页报错。
- 弹窗在「该门店暂无课程模板」时给出提示并禁用「创建排课」按钮。

## 五、遗留与建议

- 已存在的两条滨江店排课（id 23/24）**未做数据修改**：它们对滨江店会员可见、对总部会员不可见，属于规则内的正确状态。
  若确实想让总部会员看到，需要把它们改到门店 1（改 `course_schedule.venue_id`），或直接新建两条总部排课。
- `POST /api/v1/admin/schedules` 目前**没有对应的修改/删除接口**，排课一旦建错只能在界面上放着或走 SQL。
  建议后续补上「排课编辑 / 取消」，否则门店选错的操作成本偏高。
- 同类风险仍存在于其他「超管可见全部门店」的创建入口（例如商品、会员），排查"看不到数据"类问题时应先核对门店归属。
