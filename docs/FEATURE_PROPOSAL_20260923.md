## 零、先说一条我认为**必须修**的（不是新功能，是缺陷）

### 教练排课冲突检测缺失

**证据**：`CourseService.createSchedule` 只校验了三件事——结束时间晚于开始时间（第 204 行）、
场馆存在（208 行）、排课场馆与课程场馆一致（210 行）。
**没有任何地方校验"这位教练在该时间段是否已有别的排课"**（全模块 grep `冲突/conflict` 只命中一句提示文案）。

**后果**：管理员可以把同一个教练排到两个重叠时段；会员两边都预约成功，到店发现教练只有一个。
数据库里 `idx_schedule_coach_venue_time` 索引只用于查询，没有做约束。**这是数据正确性问题**，
而且越晚修，历史脏数据越多。

**建议**：建/改排课时按「同教练 + 与已有排课时间区间重叠」校验，冲突时给出具体冲突的那节课；
配合下面的批量排课做"预检"。规模：小。

## 一、第一梯队（我最推荐，收益/成本比最好）

### 1. 周期性批量排课

- **现状**：`POST /admin/schedules` 一次只能建一条排课。要建一个月的团课得点几十次，且容易排重、排漏。
- **做什么**：新增「批量排课」——选课程 + 教练 + 周几（可多选）+ 时段 + 起止日期 → 一次生成整月课表；
  生成前先做冲突预检，返回"哪些生成成功、哪些因冲突被跳过"。
- **改动面**：后端一个批量接口（复用现有建排课逻辑）+ 课程排课页一个对话框。
- **规模**：中。

### 2. 营销能力：优惠券 / 折扣 / 活动价

- **现状**：**完全没有**。26 个实体里没有任何 coupon / discount / promotion 相关表，销售开卡只能按商品标价收。
  对健身房来说，这是核心营收手段（体验券、续费折扣、老带新）。
- **做什么**：
  - 优惠券：满减 / 折扣 / 体验券；发放（手动 + 活动）；开卡时抵扣与核销；一张券只能用一次。
  - 活动价：商品在活动期内按活动价出售。
- **关键工程点（正好是你项目的强项）**：**优惠后的实收金额怎么进精确价值账**——
  退款时必须按**实付**而非标价计算可退金额。这会牵动 V9 的价值账与退款报价，做扎实了是个亮点。
- **规模**：中偏大（新增 2–3 张表 + 迁移 V11 + 两侧页面）。

### 3. 课程评价与教练评分

- **现状**：无（全模块 grep 无 review/rating 实体）。
- **做什么**：会员对**本人已签到/已消课**的课评价（1–5 星 + 标签 + 文字），同一节课只能评一次；
  教练端看自己的评分与评价列表，管理端看门店汇总与低分预警。
- **规模**：中（1–2 张表 + 会员端/教练端页面）。

## 三、第三梯队（我建议先不做）

- **真实支付接入**：涉及商户资质、回调、对账、退款原路返回，成本远超当前收益；
  现在"登记式"支付在教学项目里已经够用。
- 微信小程序 / 移动 App / i18n 多语言 / ELK 日志平台：同理。

## 四、顺手可以一起做掉的小修

- **`access_grant` 表只增不减**：门禁令牌每次取码都插一行，没有清理任务，长期会持续膨胀。
  加一个定时清理过期令牌的任务（几行代码）。
- **启用 CI**：`.github/workflows/ci.yml` 已经写好放在本地了，只差一次带 `workflow` 权限的授权就能推上去，
  之后每次推送自动跑 85 个测试 + 前端构建。

## 我的推荐组合

如果你要一个"能讲得出、有业务深度、又不至于摊太大"的组合：

> **必修：教练排课冲突检测**（数据正确性，不做会持续产生脏数据）
> **＋ 1 周期性批量排课**（日常运营刚需，与冲突检测配套）
> **＋ 2 优惠券与折扣**（补上营销短板，且能体现价值账的严谨性）
> **＋ 3 课程评价**（补上服务质量反馈闭环）

想更聚焦就砍掉 3；想更炫可以加第二梯队的 4（体测曲线，图表好看）。
